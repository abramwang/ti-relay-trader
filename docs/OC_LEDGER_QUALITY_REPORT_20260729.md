# OC / Relay 交易账表质量整改报告

更新时间：2026-07-29 17:25 Asia/Shanghai

提交给 OC 的纯修改请求见 `docs/OC_CHANGE_REQUEST_20260729.md`。

## 结论

本轮确认了两类独立问题：

1. Relay 历史账表使用 `account_id + gateway_order_id` 作为订单唯一键，但 OC/券商的 `order_stream_id` 会跨交易日复用，导致后一天订单覆盖前一天订单。成交仍按各自交易日保留，因此表现为孤立成交、累计成交量串日、终态时间残留和拒单原因残留。
2. OC 在 `order_stream_id` 为空的 ETF 篮子子单/拒单上仍会复用篮子级 `gateway_order_id`。同一账户、同一交易日的不同证券和不同 `order_id` 因此无法无损落成多笔订单。

Relay 侧问题已通过 migration `000012_trade_date_order_scope`、权威查询快照覆盖和原始流重放修复。OC 同日 ID 冲突必须在源头修复，Relay 不自行猜测或改写柜台订单编号。

## Relay 已修复

1. `orders` 唯一键和 upsert 冲突目标改为：

   `account_id + trade_date + gateway_order_id`

2. `order_events`、`fills` 外键改为同一交易日复合键并已在生产库验证。
3. 成交唯一键改为：

   `account_id + trade_date + gateway_order_id + fill_id`

4. `order.list.query` 被定义为柜台权威快照。查询页可以纠正实时事件留下的旧状态、旧数量、旧 `terminal_at`、旧拒单字段和旧 adapter 状态，不再使用 `COALESCE/GREATEST` 永久保留错误值。
5. 新增 `relayctl ledger-replay`，从 PostgreSQL `raw_stream_messages` 按“订单/查询页 -> 成交/成交页”的顺序重建账表。
6. Redis 报文缺 `produced_at` 时，使用 Redis Stream ID 的毫秒时间作为可追溯回退时间。
7. OC 未显式给 `terminal_at` 时，实时终态事件使用 `produced_at`；盘后权威查询按最终状态回看同日 `order_events` 的最早匹配终态，不再把 15:05 查询时间误记为成交或撤单时间。

终态时间回放后已无跨交易日记录。部分 OC `created_at` 只有秒级精度，而 Redis 事件为毫秒级，存在不超过 3.505 秒的采集顺序差；质量接口采用 5 秒容差，超过容差才标记 `terminal_before_created`。

## OC 必须修复：同日订单 ID 冲突

### 当前可复现样本

2026-07-29，账户 `307000051388`：

| gateway_order_id | symbol | order_id | order_stream_id | status | reject_message |
| --- | --- | ---: | --- | --- | --- |

| `BTR.90322777|J.0` | `159623` | 10 | 空 | rejected | `VIP:价格超过涨跌停板限制` |

两笔订单证券、方向和 `order_id` 不同，但共用同一个 `gateway_order_id`。

2026-07-28，账户 `314000045768`：

- `gateway_order_id=etfarb#588200.SSE#100338#s`
- 32 个不同证券
- 32 个不同 `order_id`
- `order_stream_id` 全部为空
- 均作为 `order.event` 推送

### OC 修改要求

1. `gateway_order_id` 必须在 `account_id + trade_date` 范围内代表唯一一笔订单，不能使用篮子 ID 表示多笔子单。
2. 有 `order_stream_id` 时，查询和实时推送统一使用：

   `external-huaxin-{broker_account_id}-{order_stream_id}`

3. `order_stream_id` 为空时，OC 必须生成稳定的单笔子单 ID。该 ID 至少要区分交易日、柜台 `order_id`、篮子和证券；实时推送与订单查询必须使用同一算法。
4. ETF 成分证券划转继续使用 `transfer.event / etf_component_transfer.event`，不能以多个证券共用一个 `gateway_order_id` 的 `order.event/fill.event` 表达。
5. OC 不得发送“空 `order_stream_id` + 已完成旧 gateway ID”的拒单更新。若无法确认单笔订单归属，应发送协议错误或进入 DLQ，不能覆盖另一笔订单。

## 其它质量项

2026-07-24 曾出现 114 条 `order_stream_id` 为空的 rejected 事件，被关联到此前已成交/已撤订单；15:05 的 `order.list.query` 返回了正确终态。Relay 现在会使用查询快照清除这些遗留错误，但 OC 仍应避免产生错误关联事件。

同日盘后查询仍可能返回少量 `working/queued` 订单。Relay 结算会保留 `non_terminal_order` 质量标记；OC 应保证盘后订单查询能够返回柜台最终撤单/成交状态，Relay 任务侧则需要在 15:05 启动后留出终态追平窗口。

## 联合验收

OC 更新后，以一个真实 ETF 申购/赎回篮子和一个普通股票篮子复测：

1. 同一账户、交易日内，每个 `gateway_order_id` 只对应一个 `symbol + order_id`。
2. `order.event` 与 `order.list.query` 对同一订单使用相同 `gateway_order_id`。
3. `fill.event` 的 `symbol/exchange/order_id/order_stream_id` 与关联订单一致。
4. 每笔订单 `sum(real fill.qty) = cum_filled_qty <= order_qty`。
5. 0 价 ETF 成分划转只出现在 `transfer.event`，不进入普通 `fills`。
6. 盘后查询后，除真实业务拒单外，已成交/已撤订单的 `reject_code/reject_message` 为空。
7. Relay `/performance/trade-quality` 的 `orphan_fill_groups`、证券错配和数量错配均为 0。

Redis 原始报文必须保留到联合验收结束，以便按 stream ID 逐条对照。
