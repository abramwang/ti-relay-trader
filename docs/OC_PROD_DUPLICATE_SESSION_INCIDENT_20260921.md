# OC 生产重复会话事故与处置要求

日期：`2026-09-21`

环境：生产环境，`relay.stream.v1`

状态：`根因已确认，等待清理残留进程`。Relay 生产下单权限保持关闭，未重启 Relay，未修改订单、成交或资产账本。

## 结论

运维页出现“收到交易订单，但柜台登录不正常”，不是同一个 OC 会话自相矛盾，而是每个启用账户同时存在三个持续发送心跳的 OC 进程会话：一个会话已登录并正常产生订单/成交事件，另外两个会话未完成登录并持续发布 `DEGRADED / broker_not_ready`。

`/operations` 当前按账户读取最新一条 heartbeat，因此三个会话的心跳交错时，页面会在正常和未登录之间变化。更严重的是，同一账户的三个进程使用同一 Redis consumer 身份；查询命令可能被未登录实例领取并返回 `BROKER_NOT_READY`。这不是单纯的页面展示问题，必须先消除重复进程。

## OC 与部署侧处置

1. 在测试机停止当前仍活跃的四个未登录残留进程，保留生产机上的四个健康实例，避免盘中打断正常回报链路。
2. 删除或禁用测试机遗留的生产 OC crontab，并核对测试机没有 systemd、容器重启策略或旧脚本继续拉起生产配置。
3. 核对生产机 `08:55` 启动入口只为每个启用账户拉起一个进程；测试机只能使用 TEST Redis 和 TEST 账户配置。
4. 启动入口增加账户级互斥锁或 PID 锁；同一 `env + broker + account_id` 已存在存活进程时，新进程必须启动失败并明确记录原因。
5. 不通过共享 consumer 名称来容忍多实例。当前设计边界是一账户一 OC 进程；短线重连保持同一进程会话，人工重启才生成新 `counter_session_id`。

## Relay 复验门禁

OC 清理后按以下顺序复验：

1. 等待至少一个 heartbeat 过期窗口，确认每个账户只有一个持续活跃的 `counter_session_id`。
2. 四个账户均为 `UP / running`，且 `redis_ready`、`broker_ready`、`order_snapshot_ready` 为 true；托管凭据状态及账户身份匹配。
3. 资金、持仓、订单、成交四类只读查询逐账户取得唯一 completed 终态，不再出现新的 `BROKER_NOT_READY`。
4. `cmd.trade`、`cmd.query` consumer group 均为 `pending=0, lag=0`，输出流无重复订单/成交事件。
5. 对 5 条历史 `QUERY_INTERRUPTED` DLQ 完成关联审计，再决定 ACK；保留 Redis 原始消息和 PostgreSQL 审计。
6. 生产下单权限继续保持关闭；开放生产交易必须由用户另行明确授权。

## Relay 后续增强

重复实例清理后，Relay 增加账户级多活会话检测：在 heartbeat 新鲜窗口内出现两个及以上 `counter_session_id` 时标记 `OC_MULTIPLE_SESSIONS`，而不是只展示最后一条心跳。同时，新健康 heartbeat 应结束旧的临时 `BROKER_NOT_READY` 展示，但不得掩盖多会话故障。
