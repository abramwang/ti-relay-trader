# OC 生产重复会话事故与处置要求

日期：`2026-09-21`

环境：生产环境，`relay.stream.v1`

状态：`已隔离并完成业务复验`。Relay 生产下单权限保持关闭，未重启 Relay，未对历史订单、成交或资产账本执行人工修补或删除。

## 结论

运维页出现“收到交易订单，但柜台登录不正常”，不是同一个 OC 会话自相矛盾，而是每个启用账户同时存在三个持续发送心跳的 OC 进程会话：一个会话已登录并正常产生订单/成交事件，另外两个会话未完成登录并持续发布 `DEGRADED / broker_not_ready`。

`/operations` 当前按账户读取最新一条 heartbeat，因此三个会话的心跳交错时，页面会在正常和未登录之间变化。更严重的是，同一账户的三个进程使用同一 Redis consumer 身份；查询命令可能被未登录实例领取并返回 `BROKER_NOT_READY`。这不是单纯的页面展示问题，必须先消除重复进程。

连续 12 秒复查显示，先前每户两个未登录会话中的一个已经不再新鲜，但以下四个测试机残留会话仍每约 5 秒发布 heartbeat：

通过生产 Redis `CLIENT LIST` 和短时只读 `MONITOR` 交叉定位，当前连接来源如下：

| 公网源 IP | 连接特征 | heartbeat 归属 | 判断 |
| --- | --- | --- | --- |
| `210.22.105.118` | 4 个 `XADD` + 4 个 `XREADGROUP` | 四个启用账户的健康会话，组件名含 `.prod.`，`credential_status=loaded` | 正常生产新版 OC |
| `117.186.20.114` | 5 个 `XADD` + 5 个 `XREADGROUP` | 四个未登录异常会话，以及已停用账户 `307000051389` 的旧会话 `hxproc-39b89e690723ef49` | 仍在运行的旧版 OC 主机或 NAT 出口 |
| `114.88.167.196` | Relay 状态读取连接 | 无 OC heartbeat | Relay 服务出口 |

异常源的第五个进程持续向 `relay:prod:v1:huaxin:307000051389:hb` 发布 `UP` heartbeat，但该账户已在 Relay 配置中停用，所以常规 `/operations` 页面不会展示它。这个指纹说明异常源仍运行着停用前的五账户旧启动配置。

Redis 只能提供 TCP 对端公网地址，若 `117.186.20.114` 是 NAT 出口，无法从 Redis 反推出内网主机名。需要在候选机器执行 `curl -4 https://api.ipify.org` 对照，并检查 root、服务用户、systemd、supervisor、Docker 和其他守护入口。

用户随后在生产 Redis 安全组中将 `117.186.20.114` 加入黑名单。旧连接不再产生 heartbeat，但 TCP 会话仍残留在 Redis 客户端表中；经用户授权，Relay 按已核对的 client ID 精确执行 `CLIENT KILL`，6 条剩余连接均返回 `killed=1`。立即检查、10 秒后检查及业务复验完成后的再次检查均未发现该来源重连。

## OC 与部署侧处置

1. 定位公网出口为 `117.186.20.114` 的主机或 NAT 网络，停止其中五个旧版 OC 进程；不要操作来源 `210.22.105.118` 的四个健康生产实例。
2. 检查异常主机所有用户的 crontab，以及 systemd timer/service、supervisor、Docker 重启策略、tmux/nohup 和旧启动脚本，避免进程再次拉起。
3. 删除异常主机上的生产 Redis 配置或凭据；非生产主机只能使用 TEST Redis 和测试账户配置。
4. 启动入口增加账户级互斥锁或 PID 锁；同一 `env + broker + account_id` 已存在存活进程时，新进程必须启动失败并明确记录原因。
5. 不通过共享 consumer 名称来容忍多实例。当前设计边界是一账户一 OC 进程；短线重连保持同一进程会话，人工重启才生成新 `counter_session_id`。

## Relay 复验门禁

OC 清理后按以下顺序复验：

1. 等待至少一个 heartbeat 过期窗口，确认每个账户只有一个持续活跃的 `counter_session_id`。
2. 四个账户均为 `UP / running`，且 `redis_ready`、`broker_ready`、`order_snapshot_ready` 为 true；托管凭据状态及账户身份匹配。
3. 资金、持仓、订单、成交四类只读查询逐账户取得唯一 completed 终态，不再出现新的 `BROKER_NOT_READY`。
4. `cmd.trade`、`cmd.query` consumer group 均为 `pending=0, lag=0`，输出流无重复订单/成交事件。
5. 对 5 条历史 `QUERY_INTERRUPTED` DLQ 完成关联审计，再决定 ACK；保留 Redis 原始消息和 PostgreSQL 审计。
6. 生产下单权限继续保持关闭；开放生产交易必须由用户另行明确授权。

## Relay 后续增强

重复实例清理后，Relay 增加账户级多活会话检测：在 heartbeat 新鲜窗口内出现两个及以上 `counter_session_id` 时标记 `OC_MULTIPLE_SESSIONS`，而不是只展示最后一条心跳。同时，新健康 heartbeat 应结束旧的临时 `BROKER_NOT_READY` 展示，但不得掩盖多会话故障。
