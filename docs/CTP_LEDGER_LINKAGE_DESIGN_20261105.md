### 11-07 心跳解码与 TEST 会话失效保护

新增`heartbeat.go/test_session.go`，只接既有`messages.json/heartbeat_read_only`的draft.2字段，不修改共享JSON、wire、Meridian或华鑫逻辑。**这是内部消费保护接线，不是实际OC心跳订阅或在线准入验收。**

- 已接收消息的produced_at决定剩余有效期，不以重复收到时间刷新。相同entry同原文、相同message同原文换entry均不续期；entry回退/同号异体、message同号异体、新message源时钟不前进、陈旧或过度超前的时间均关闭当前guard。有效小幅未来时间最多给予一份本地MaxAge，不额外延长；真实接收时使用本机单调时钟保存期限。单guard最多512个不同message，超限停止，不驱逐旧身份后继续。

### 11-06 已登记上下文分发与联合质量检查

新增`stream_dispatch.go/stream_quality.go`，复用既有表结构和原子交接，不新增wire、迁移或后台服务。

`NewStreamDispatcher`构建不可变目标白名单，最多128项。只绑定既有event scope或已关联CommandID的query batch；核对物理Stream、路由、原生投资者/用户和owner，拒绝跨环境、错角色、重复目标及退休查询。事件按显式绑定的TradingDay和counter_session_id选择目标；查询按已登记原命令origin选择目标，不能用第一条回报创建命令、推断交易日或建立新会话。构造参数仍须来自调用方已核实的生命周期/请求事实，**这不是OC来源认证、凭据接线或会话自动发现的实现**。事件wire没有新增连接代次字段。

`Dispatch(afterID,limit)`每次扫描1..256条待处理原文，不创建goroutine，不重发任何柜台命令。坏JSON、错误路由、未知日/会话/origin保持transport pending，返回有界原因列表，不自动隔离、丢弃或改原文。扫描游标跨过这些记录继续处理后项；一轮结束返回`CycleComplete=true/NextAfterID=0`，调用方须退避后重新扫描，避免等待身份的旧项永远漏掉。此游标仅控制本轮扫描，不是Redis读取位点或完成证明。

已匹配目标仍经完整事件/查询校验和原子`ForwardEvent/ForwardQuery`交接；事件不在这里自动Process，交易查询也不自动ApplyTradeQuery。数据库失败、owner变化或绑定失效会返回错误，保留此前已提交结果，返回的游标不会跳过失败项。重建dispatcher需重新绑定可信上下文，不从入站消息恢复信任。查询elapsed从原始本地请求StartedAt计时，不使用回报时间或重建dispatcher时间；StartedAt零值/未来/回退到已记录elapsed之前拒绝。无消息时的超时仍由调用方显式Advance，不能把本组件称为已完成后台调度器。

`InspectDeliveryQuality`在**单个只读、可重复读PG事务**中联合检查：

1. event/reply两个当前handle必须同路由/原生作用域/SourceID，owner和审计计数一致；两条物理Stream全保留期的pending/quarantined都计入阻断，不借换日隐藏未知消息。
2. 指定交易日事件的pending/waiting_identity/rejected/conflict，以及该日交易投影的缺失、checksum、冲突和未关联成交。delivered不是applied，applied也不代表成交已经关联完整。
3. 已应用交易查询后续变为非ready仍阻断；新查询成功不会自动清除这类历史证据。
4. 四类查询均要求latest target=current published、ready、未退休、当前QueryStore owner，以及明确的TradingDay/counter_session_id/connection_generation和原生身份一致。校验原CommandID证据与候选checksum/context；订单/成交查询还须有对应交易日的应用标记。
5. 最新查询失败/未完时，即使历史快照还能用于页面参考，也不能通过本检查；不修改既有`Current`的历史可读规则。未知/缺失/读取错误一律保持Blocked，不将空存储、旧会话或未应用查询当作成功。

- `StreamStore.Open`显式登记可信路由、原生身份、event/reply角色及持久Redis部署标识`SourceID`。物理Stream唯一绑定这些配置，不含TradingDay，不因日切清空或另起位点。初次从`0-0`开始，不从`$`跳过历史；旧配置/原生用户/源部署漂移拒绝，不静默重置。`SourceID`不是密码或Redis进程run_id，也不能证明客户端实际连到了正确Redis，调用方仍负责固定客户端和授权来源。
- 每次明确接管生成新owner；必须先协调停止旧读取者，不是自动抢占或租约选主。原文提交、状态读取和移交均检查owner；在Redis读取期间被接管的旧进程不能再落库/推进位点。下游已持久的事件处理仍使用既有幂等机制。
- `Capture`以当前位点作CAS，在同一同步提交事务内保存原body字节、SHA256、`pending`责任及新位点；原文不是JSONB，不因UTF-8/JSON非法而丢弃。严格比较两个uint64组成的Redis ID，拒绝溢出、非规范文本、乱序和未知旧entry。原entry同字节可在重读当前位点后幂等重投，同entry异体失败，不覆盖原证据。提交结果不明时重读数据库，不能假设成功或从最新Redis位置跳读。
- `ReadOnce`使用调用方提供的go-redis只读接口，执行前后`XINFO STREAM`及一次有界非阻塞`XREAD`。检查可观测的删除/裁剪、回退、错误Stream、条数、entry顺序、body类型/大小，异常不推进位点；空读不制造消息。读取前后检查不是所有删除重建/备份恢复场景的证明，不能替代保留策略及明确的源变更流程。
- 本轮适配要求`MaxDeletedEntryID/EntriesAdded`等Redis元数据，缺失则停止；需后续真实Redis版本/权限验收。标准外层应只有body字段，未知外层字段/缺body拒绝整批，责任留在源端，不假装已审计未知结构。go-redis解析后的字段map不提供重复字段名的原始RESP证据，此边界仍待真实传输验证；持久化范围为收到的body，不是完整RESP字节。字节预算也不是网络解码前RSS上限。
- `Pending(afterID,limit)`按本地收件ID分页，可跳过前部等待记录处理后续项；一轮结束需从0开始重新扫描。`Record/Status`保留原文和pending/quarantined/delivered计数；`Quarantine`只能显式记录待核查原因，不删除、修复或自动解除阻断。待处理/隔离数据不能作为完整账本，未来聚合准入还必须同时检查这些状态及下游查询/事件质量，不能只读`TradeStore.Read`或看delivered计数。
- `ForwardEvent`核对已登记原生作用域和显式交易日，复用`receiveEventTx`，在同一事务内写事件收件箱及带FK的交接标记；错日/坏报文留在源收件箱待调查，不用当前日硬塞。交接不意味着已应用，未知本地报单仍在事件层waiting_identity，原始成交仍可pending关联。
- `ForwardQuery`核对已登记CommandID/批次/原生身份和原origin，复用现有严格关联校验；原页、批次/候选/指针及交接标记同事务提交。未知批次不能从reply反向建请求，任一步失败保持原收件pending。重启后旧查询仍需显式Recover；已中断旧半页不借收件箱恢复为成功，晚到旧页留存待调查，新采样必须新命令。
- 接收一块最多256条、8MiB；每条物理Stream整个原型保留期累计最多50,000条、64MiB原body，**不是每日重置**。和下游各自预算分别计数，达到上限停止，不丢旧原文。迁移down发现任何收件原文就拒绝，不删除证据迁就降级。自动保留/归档和全局背压未完成，不能将本原型直接长期上线。

### 持久化与恢复增量实现

新增 `internal/futures/query_store.go`，迁移 `000033_futures_query_storage`，只在本机临时PostgreSQL验证。实际表为`futures_query_heads/batches/observations/snapshots`四张；资金/持仓分别保存整批不可变类型化JSON候选，尚未实现下文拟议订单/成交和逐行检索表。原文使用BYTEA及SHA256，保留非法UTF-8、空体、重复JSON键和金额文本；不用JSONB重排原始消息。内部context/limits用JSONB，存储格式版本1不改变wire版本。

- `Register`登记不可变请求及本地限制，并选定同一路由/查询类别的下一发布目标；重复登记不能重新选中旧批次。同一scope+原命令只能有一批；scope包含环境、路由券商、gateway、账户、action，不混用股票表或生产/测试事实。
- `Ingest`在作用域行锁下重放已持久证据，验证新输入，并在同一事务保存原文、处理状态、完整候选及发布指针。事务设置`synchronous_commit=on`。返回无数据库错误只说明该输入及处理结果已提交；`rejected/foreign/failed`仍不是业务成功，也没有实现Redis ACK/消费位点。
- 同来源Stream/entry及相同原文只重放；同message_id不同来源保留各自审计但不重复投影。同来源不同体保留两份并使批次无效；晚到协议冲突也使历史/当前快照读取失败关闭，旧候选物理保留供排错，不静默退回另一个快照。
- 完整结果与发布指针同事务提交。非最新注册目标仍可保存完整历史，不能覆盖新目标；新查询失败时旧完整、同会话/交易日快照保留原始captured_at，不刷新为当前查询时间。空完整持仓明确为空数组；资金不因失败变零，不把资金及持仓两个独立查询包装成原子经济快照。
- 每个`QueryStore`接收器实例生成随机owner fence，需在该接收器生命周期内复用同一实例；重建实例不能续用旧进程单调时钟或拼接旧半页。`Recover`是调用方停掉旧接收器后的显式操作，只处理中断旧半页并退休旧owner对应批次；已完整结果保留历史，不移发布指针。退休标志也拒绝旧writer后续提交，避免旧对象误复活。
- `Current`要求调用方显式给出当前TradingDay、OC会话/代次及原生BrokerID，并同时核对最新目标和当前候选；还限制为本接收器owner且未退休。`Snapshot`只读完整有效历史，不授予当前readiness。新进程必须重新取得当前证据，不能把历史恢复当新鲜心跳/账户交易准入。
- `Advance`持久化缺页超时，`Interrupt`记录断线/取消的本地原因，不伪装柜台失败。调用方负责单调经过时长与定时推进、正确请求绑定和停旧进程；没有后台自动计时器、旧SDK请求重发或新交易指令。
- 本地审计上限每批1024份独立输入、32MiB原文；超限或数据库故障不提交输入且返回error，未来消费者必须保留上游待处理责任、背压并显示不可用，不能截断原文或ACK。context限64KiB。当前事务内有界重放适合此隔离实现，但尚未做大批次性能验收、全局配额、保留期/清理和未完成批次自动发现。

- `ApplyTradeQuery`只接已持久ready的订单/成交查询，按原页序与行序取原始行，不用类型化结果重新序列化替代审计。稳定行source_id来自批次ID/页索引/行索引的结构化哈希；原完整消息继续留在查询观察表。全批事实、订单投影、关联、审计与`futures_query_trade_applications`标记同事务提交，锁顺序为查询作用域/批次，再交易作用域。
- 该操作不是快照覆盖：空查询保存0行应用标记但不清订单/成交；未知订单的成交仍pending不造单；费用是证据版本不是新增成交。合并全批时只重放一次已有行审计并统一写投影，不逐行重复读取重建整本账。订单保守状态规则仍可能因历史矛盾而阻断，Applied不等于质量通过。
- `ListUnappliedTradeQueries(limit=1..256)`可在“查询完整已提交、尚未应用”窗口重启后发现批次；应用标记与账本同事务，丢返回后重复调用只返回Replayed。已完整旧owner/旧会话结果可以补历史事实，不移动当前查询指针、不授予readiness；旧半页不续接，失败/过期/无效批次不应用。生命周期自动扫描及Redis位点仍未实现。

### 本地报单登记与事件持久收件

- 同entry原字节重投复用收件记录；同message_id原字节换entry保留独立接收证据，账本source按作用域+message_id去重。entry或message_id同号异体保留双方并置conflict，已应用事实不物理删除；冲突记录的原消息再换entry也继续冲突，不能通过再次发送原体洗掉标记。
- `Process`重新校验完整事件和审计指纹。已登记本地gateway必须匹配原message_id及合约/方向/开平/套保，订单量价匹配；可选client/request/correlation/idempotency若出现也须一致。成交允许先于订单，不用成交价冒充委托价，单笔量不能超原委托量。批量子单共用父message_id，但分别核对自己的意图。
- 未登记的普通gateway进入waiting_identity，不凭本地查不到推断外部。只有已经通过确定性原生ID校验且无origin的external-ctp-v1事件，才按**受信任OC发布者的外部身份声明**接收；这不是Relay独立证明外部所有权。带origin却未有登记的外部提示仍等待核实。来源认证、授权配置加载和真正发单前登记顺序必须在后续运行接线落实，不能将此内部API开放给事件发送者反向登记自己。
- 应用的原始payload、行事实/关联/质量以及inbox处理状态同事务提交；事务失败回滚账本写入，先前完整原文仍pending。成功Applied仅说明事件处理落库，成交可仍pending关联或存在经济冲突，不等于账户账本完整。后续调用`TradeStore.Read`同时读取查询批次质量和所有非applied事件状态；等待/拒绝/冲突均显式阻断，不能只读底层逐行JSON当质量通过。
- `Pending(scope,afterID,limit)`按ID游标扫描pending/waiting_identity（每页1..256），避免前部等待身份的记录遮住后续事件；新接收器可恢复，调度/退避由调用方负责。waiting可在独立可信登记补齐后再处理；rejected/conflict不自动清除，尚无人工修正/授权重分类接口。这个扫描不是Redis位点，也不重发柜台指令。

## 1. 为什么不能直接套股票表

当前 `internal/trading/schema.go` 的Order/Fill使用int64 order_id、float64价格/费用；股票持仓模型没有期货方向、今昨桶和保证金。`migrations/postgres/000012_trade_date_order_scope.up.sql` 的成交唯一键包含gateway_order_id，且成交必须引用订单。期货不能沿用这些假设：

- TradeID的去重不能因后来补全gateway_order_id而改变。
- 无已知订单时，成交仍是真实事实；不能伪造委托量、委托价和状态来满足外键。
- 查询有OrderSysID但缺已确认自然时间，不能用查询接收时间补委托/成交时间。
- CTP资金是权益/保证金作用域，合约名义价值不是股票市值，不能加入股票资产/绩效。

因此复用已有路由、命令和审计基础设施，但增加期货专用事实、关联、快照模型。A股表、API行为和既有历史绩效保持原状。

## 2. 本轮可执行参考模型

`tests/ctpcontract/fill_linkage.py` 是内存、离线的单账户身份关联模型。它接收显式可信路由、原生BrokerID/InvestorID授权绑定、证据身份、原始行JSON；不是Redis消费者，也不是持久暂存实现。

模型假定调用方已经核实来源和订单证据；配置值相等不是登录认证，字典中的订单也不能证明本地发单前持久身份已经存在。实际消息来源、命令关联及原生别名授权仍须运行时和持久层验证，不以这些合成测试代替。

行结构复用已有查询schema。只有内部成交候选允许缺gateway_order_id，以验证“已知TradeID/OrderSysID但未关联逻辑订单”；**公开query-page.schema.json不变**。这不是要求OC立即发送缺字段的fill.event，传输层如何承载未关联事实留给统一稿确认。缺TradeID/OrderSysID等关键事实的行进入原始证据/异常集合，不补造编号来形成可去重成交。

来源证据ID由调用方提供，例如经可信分发的Stream/entry/行号组合，不从订单ID猜。相同证据ID与原始体完全相同视为重投；不同体保留两份并记录冲突。新证据ID下重复的业务事实只形成一笔成交、多份证据。错误原文仍保留；达到资源上限时明确拒收，调用方必须继续持久保存/重试，不能假装已安全ACK。内存模型本身没有ACK能力。

### 关联规则

| 事实或条件 | 行为 |
| --- | --- |
| 成交先到，订单未到 | pending；不创建假订单、不计为已关联账本 |
| 原生SysID缺失的订单先到 | 仅保存订单身份锚；相同gateway提示不足以关联成交 |
| 后续同一逻辑订单补齐SysID | 在经济字段一致且SysID无竞争归属时增加原生关联，再检查pending |
| 唯一原生订单存在 | 还需合约/交易所/方向/开平/套保一致，才能关联 |
| 成交含本地gateway提示 | 必须等于已有逻辑订单；不同本地ID不自动互认 |
| 成交含既有算法派生的external提示 | 原生身份严格一致且已有唯一订单时，可关联该逻辑订单；不创建第二笔成交/订单 |
| 两笔实际订单争用同一SysID | 保留证据并阻断，不按先到/后到自动合并 |
| 同一gateway改SysID，或改变合约/原委托数量/价格 | 冲突，不覆盖身份锚；修正需要独立授权证据和审计流程 |
| 同一TradeID数量、价格、合约、方向、开平、SysID不同 | 执行事实冲突，不覆盖、累加或静默去重 |
| 源成交时间null后获得实际时间 | 保留两份证据；两个已知时间矛盾则阻断，不用接收时间选胜者 |
| 费用从null更新、有不同费用快照 | 保留费用证据版本，不重复成交，不相加、不自动选最终交割费用 |

去重身份沿用既有七段长度框定哈希：环境、路由券商、逻辑账户、Gateway、TradingDay、交易所、TradeID。OrderSysID是关联和一致性约束，不改变成交唯一键。原生BrokerID/InvestorID必须通过配置授权绑定另验；UserID不是InvestorID，也不能用采集登录用户覆盖外部原用户。

自然成交时间不决定TradingDay，跨日复用相同TradeID必须是不同事实。counter_session_id保留各次来源，不参与成交重新计数；原生FrontID/SessionID与OC进程会话分开，不用当前会话覆盖历史身份。

已关联唯一成交数量之和不能超过订单原委托量；超量保留所有事实并阻断，不截断到委托量。订单快照cum_filled_qty可能落后于实时成交，不能据此将新成交判为假数据；跨流最终数量闭合是另一步对账。

模型的`blocked`仅指本次身份/执行事实关联是否存在pending或冲突，**不是完整账本、资金、费用最终性、会计绩效或下单readiness结论**。订单状态仅作为原证据保留，不以最后收到的快照选择当前生命周期。本轮没有实现冲突消除或人工修正接口。

## 3. HTTP / SDK / Wire / DB 字段矩阵候选

以下是设计，不是已发布端点/SDK类型。现有统一账户/订单/成交入口继续复用，按账户product_type与schema/capability分流；旧股票消费端不能被动解析期货行。实际字段冻结后才修改Go/Python运行模型。

| 概念 | OC wire事实 | HTTP / SDK候选 | 持久表达及禁止事项 |
| --- | --- | --- | --- |
| 路由 | routing.env/broker_id/account_id/gateway_id | 账户产品类型及路由沿用；环境仍由服务端选择 | 全作用域绑定；测试/生产库继续隔离，不能仅按原生投资者区分 |
| 标的 | symbol原生InstrumentID、exchange原码 | 保留原码；另给Meridian security_id映射及映射状态 | 原码与标准关联分列，保留映射来源/版本；不拼后缀、不统一大写、不用主连发单 |
| 逻辑订单 | gateway_order_id、client_order_id | 字符串，CTP不输出伪造的数字order_id=0 | 原逻辑ID不可变；别名/原生键单独存储 |
| 原生身份 | native_ids各编号、BrokerID/InvestorID/UserID | 字符串编号保前导零，SDK原整数仍显式整数/null | 原始字节审计与规范值分开；不强转BIGINT、不猜身份关系 |
| 交易时间 | TradingDay、nullable submitted_at/matched_at、counter_session_id | 分别显示交易日、发生时间、采集时间；未知明确null | DATE与TIMESTAMPTZ分列，并留来源；不使用数据库默认now代替发生时间 |
| 手数/方向 | order_qty/qty、B/S、O/C/CT/CY、speculation | SDK类型化整数手数，开平显式必填 | 非负/正整数约束；买卖不是持仓多空，不能按股票股数或T+1计算 |
| 价格 | 已验证普通十进制字符串 | 返回字符串；SDK可显式转Decimal，不隐式float | 原文TEXT保留；定点/NUMERIC投影需编码边界确认，不沿用NUMERIC(20,6)舍入 |
| 成交费用 | fee文本或null、fee_complete、原始范围证据 | 未知不是0；费用完整关联不等于最终清算 | 独立版本证据，禁止累计相同记录多次；最终标记须另有来源证明 |
| 查询状态 | 原命令、ticket、SDK号、代次、chunk、结果证据 | 区分pending/failed/完整结果及as-of，不把旧快照更新时间刷新 | 批次级状态与行事实分离；原始完成不等于允许发布 |
| 期货资金 | futures.scope、balance/available/margin/profit等 | 期货专用结构和全部作用域，scope_verified保留 | 不跨币种/BizType求和；不把名义价值/保证金再加Balance，不填股票net_asset |

HTTP正常成交列表、SDK回调如何区分待关联事实仍需统一稿确认。候选原则是原始审计可见、状态可观测，只有明确关联的类型化成交进入普通交易回调；不能悄悄丢消息或把不完整事实回调成已成交正常订单。回调幂等键与成交事实身份固定，关联/费用更新需表达修订而不是新成交。

| 原始证据与处理结果 | 现有raw审计扩展或futures_observations | 来源身份、完整body、接收时间、内容指纹和处理结果；不同体冲突不能覆盖原文 |
| 订单事实与当前投影 | futures_orders及版本证据 | 作用域+TradingDay+gateway唯一；状态合并不由查询到达顺序决定 |
| 原生别名 | futures_order_native_aliases | 全作用域+TradingDay+ExchangeID+OrderSysID唯一；会话OrderRef另类键，不与SysID混用 |
| 独立成交事实 | futures_executions | 七段原生身份唯一，与gateway是否已有无关；保存规范经济字段和全部来源证据 |
| 成交关联 | futures_execution_links | execution唯一关联一个真实order；可无关联行，pending不违反订单外键 |
| 冲突/费用修订 | 证据关联及质量记录 | 原记录不可覆盖，修正需指向旧证据并标版本、原因及授权；费用与成交事实去重分开 |
| 查询采集/完整性 | futures_query_batches及页证据 | 原命令/请求/代次绑定、页指纹、资源界限、唯一成功终态、冲突/过期状态 |
| 资金/持仓快照 | futures_asset_snapshots / futures_position_snapshots | 批次+完整原生维度唯一；发布指针只切到已校验完整批次，不逐行覆盖当前视图 |

拟定处理顺序：

1. 持久保存原始接收事实和去重/冲突结果；解析失败不能变成业务成功，身份不全仍可保存审计。
2. 在事务内幂等写入规范事实、关联或pending状态，以及可重做处理记录；不得为外键补假订单。
3. 订单补齐时，同一事务核对唯一映射、重查pending、关联与数量质量；竞争写入依赖唯一约束/锁，不靠单进程字典。
4. 事务提交后才能推进消费位点/ACK；已落原文但待处理时必须有持久重试责任，不能以ACK代表已经进入有效账本。
5. 查询快照完整并仍属于有效代次时原子发布资金/持仓批次；失败保留旧快照及真实采集时间。订单/成交查询是补充事实，不是全表删除重建，不能覆盖更晚实时事件。
6. 晚到冲突标记批次/关联不再可信，保留已发布历史及证据，启动核查；不得假装撤回外部已经消费的回调或静默回滚券商事实。

具体SQL、事务隔离、outbox/ACK重启恢复尚未实现或测试。单次原子发布不等于柜台跨资金/持仓查询原子快照；每类采集时间分别保留。超时pending不自动丢弃、终态化或授权补单/撤单。
